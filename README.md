# NSL — Nintendo Switch Library

**NSL**은 PC에 보관한 Nintendo Switch 게임 파일을 검색·분류하고 관리하는 **Windows용 네이티브 라이브러리 관리 프로그램**입니다. 게임, 업데이트, DLC 정보를 한 화면에서 확인하고 파일과 타이틀 데이터베이스를 함께 관리할 수 있습니다.

**[최신 버전 다운로드](https://github.com/UzuCore/NSL/releases/latest)** · **[전체 릴리스](https://github.com/UzuCore/NSL/releases)** · **[수동 빌드 실행](https://github.com/UzuCore/NSL/actions/workflows/windows-build.yml)**

> **개발 현황 (2026-11-20, KST)**
>
> 최신 기능 배포본은 **[Stage 20 / r22](https://github.com/UzuCore/NSL/releases/tag/build-20261120-072438-KST-r22)**이며, 소스 기준 커밋은 `d09c91a`입니다. 현재 `main`에는 이후 작업인 **[P2 앱 모듈화 (`af04b32`)](https://github.com/UzuCore/NSL/commit/af04b322921f34c5b06a49f0aed1e28c50326a7b)**와 **NSRP 참고 PFS0/HFS0 롬 컨테이너 파서 통합**이 추가되어 있습니다. **이후 소스는 컴파일·런타임 검증 및 새 릴리스 빌드 전 상태**이므로, 최신 다운로드 파일과 최신 소스가 동일한 커밋이라고 간주하지 마세요. **빌드와 배포는 사용자 수동 실행 전용**입니다.

## 주요 기능

| 분류 | 기능 |
| --- | --- |
| 파일 관리 | `NSP`, `NSZ`, `XCI`, `XCZ` 검색 및 라이브러리 등록, 네이티브 PFS0/HFS0 컨테이너 검증 |
| 게임 정보 | 게임·업데이트·DLC 구분, 버전 확인, 누락된 업데이트·DLC 조회 및 지역별 제목 표시 |
| 타이틀 DB | `borntohonk/titledb` 기반 게임 이름·메타데이터 매칭, 압축된 제목 DB 다운로드 및 변경 확인 후 갱신 |
| 미디어 | 게임 아이콘과 스크린샷 수집 및 캐시 관리 |
| 목록 UI | 리스트·그리드 보기, 검색·정렬·필터, 최대 5개 폴더별 탭, 게임 상세 정보 패널, 키보드 탐색 |
| 파일 도구 | 파일명 정리, 라이브러리 CSV 내보내기, `NSZ → NSP` 및 `XCZ → XCI` 변환 |
| 스토어 | 제목·장르·형식·언어 검색/분류, 타이틀 상세 정보, 토렌트 다운로드 전 파일·하위 폴더 선택 |
| 다운로드 | 토렌트 일시정지·재개 및 진행 상태, 활성 시드·피어 수, 삭제 확인 및 파일 보존 선택 |
| 성능·안정성 | 목록 가상화, 비동기 이미지 로딩, 증분 스캔, 타이틀 DB 검증 캐시, NCZ 지연 디코딩, 작업 진행률·취소, 중복 실행 보호 |
| 업데이트 | GitHub Releases의 검증된 ZIP을 이용한 프로그램 자체 업데이트 |

게임 파일을 분석하고 압축 형식을 변환하는 주요 기능은 **Rust로 직접 구현**되어 있으며, 별도의 Python 실행 환경이나 `nstool`, `hactool`, `nsz.exe` 설치가 필요하지 않습니다.
컨테이너 인덱스 파서는 NSRP의 MIT 라이선스 Rust 코드를 참고해 NSL의 NSP/NSZ·XCI/XCZ 읽기 경로에 통합했습니다. **롬 분석·압축 변환에 외부 콘솔 도구를 실행하지 않으며**, 탐색기 열기·사용자 지정 에뮬레이터 실행·자체 업데이트에 필요한 Windows 시스템 프로그램 호출은 별도로 유지됩니다.

## 다운로드 및 사용

1. **[Releases](https://github.com/UzuCore/NSL/releases/latest)**에서 최신 `nsl-win64.zip`을 다운로드합니다.
2. ZIP을 원하는 폴더에 압축 해제하고 `nsl.exe`를 실행합니다.
3. 설정에서 스캔할 게임 폴더를 등록합니다. **최대 5개 폴더**를 지정할 수 있습니다.
4. 게임 파일을 스캔하고 필요에 따라 타이틀 DB를 갱신하거나 **미디어 수집**을 실행합니다.

일부 암호화된 게임 파일의 메타데이터를 읽으려면 사용자가 **직접 준비한 적법한 키 파일**이 필요할 수 있습니다. 게임 파일, 개인 키 및 사용자 데이터는 이 저장소와 공식 배포 ZIP에 포함되지 않습니다.

### 지원 환경

- **운영체제:** Windows x64
- **배포 형태:** 포터블 ZIP (`nsl.exe` 및 필수 파일)
- **저장 방식:** SQLite 기반 로컬 라이브러리와 JSON 설정

## 화면 구성

- **라이브러리:** 보유 게임, 업데이트, DLC 및 누락 항목을 검색·정렬·필터링합니다.
- **상세 정보:** 선택한 게임의 파일, 게임 정보, 스크린샷, DLC를 확인합니다. 선택을 바꾸어도 사용자가 조절한 상세 패널 너비가 유지됩니다.
- **스토어:** 오른쪽 패널에서 제목·장르·파일 형식·언어 등을 검색/분류합니다. 게임명은 설정의 **이름 표시 우선순위**를 따르며, 카탈로그 목록과 상세 정보를 함께 볼 수 있습니다.
- **다운로드:** 스토어와 오른쪽 패널 너비를 공유합니다. 다운로드명을 왼쪽 정렬하고 진행 상황, 속도, **현재 연결된 활성 시드·피어 수**를 표시합니다. 연결 통계를 알 수 없을 때는 `—`로 표시하며, 전체 토렌트 스웜 인원과는 다릅니다.
- **설정:** 스캔 폴더, 표시 방식, 이미지 수집, DB 소스 등 환경을 조정합니다.

대용량 라이브러리에서도 목록을 먼저 표시하고 이미지는 필요할 때 불러오도록 설계했습니다. 스캔과 다운로드 등 장시간 작업의 상태는 하단 진행 표시줄에서 확인할 수 있습니다.

### 스토어에서 다운로드하기

1. 스토어에서 원하는 항목을 선택하고 다운로드를 누릅니다.
2. 토렌트의 파일 목록이 나타나면 **탐색기 형태의 트리**에서 `+`/`−`로 하위 폴더를 펼치거나 접고, 원하는 파일만 선택합니다. **전체 선택·전체 해제·모두 펼치기·모두 접기** 버튼도 사용할 수 있습니다.
3. 선택한 파일을 다운로드하고 다운로드 탭에서 진행 상태를 확인합니다. 여러 하위 디렉터리도 탐색할 수 있습니다.
4. **삭제**를 누르면 항상 확인창을 표시합니다. **목록만 삭제(파일 유지)**, **파일까지 삭제**, **취소** 중 원하는 동작을 직접 선택해야 합니다. 삭제 버튼을 누르는 것만으로 파일을 바로 지우지 않습니다.

다운로드와 파일 선택은 본인이 이용 권한을 가진 자료를 대상으로 사용하세요. 토렌트 연결 환경이나 트래커 상태에 따라 파일 목록과 시드·피어 통계가 즉시 나타나지 않을 수 있습니다.

### 타이틀 데이터베이스

게임 제목 및 언어 정보의 기본 소스는 [borntohonk/titledb](https://github.com/borntohonk/titledb)입니다. `titles.json.zst`를 스트리밍으로 압축 해제하고, `versions.json`·`KR.ko.json` 등과 함께 로컬 DB를 갱신합니다. 검증된 데이터가 변경되지 않았다면 불필요한 재처리를 건너뛰며, 필요한 파일을 내려받는 구간에는 진행 상태를 표시합니다.

공식 ZIP은 빌드 환경의 공개 타이틀 DB 보유 여부에 따라 이 데이터 파일들을 포함하지 않을 수 있습니다. **타이틀 DB가 ZIP에 없다는 사실만으로 빌드 실패를 뜻하지 않으며**, 프로그램에서 별도로 갱신할 수 있습니다.

## 소스 검증 및 수동 빌드

**Rust stable**, Cargo, Git, Windows PowerShell이 설치된 Windows x64 환경을 사용합니다.

```powershell
git clone https://github.com/UzuCore/NSL.git
cd NSL

# 모듈화된 최신 소스의 컴파일·회귀 검증 (수동 실행)
python -B scripts/qa-rom-index-readonly.py  # 원본 롬을 수정하지 않는 독립 검수
cargo fmt --all -- --check
cargo test --locked --all-targets
cargo clippy --locked --all-targets -- -D warnings

# 검증 후 실행파일과 배포 ZIP 생성 (수동 실행)
.\build.bat
```

`build.bat`은 다음 작업을 순서대로 수행합니다.

1. `cargo build --release --locked`로 Rust 릴리스를 빌드합니다.
2. 배포 파일과 라이선스 고지를 ZIP으로 묶습니다.
3. ZIP 안의 파일 목록, 매니페스트 및 SHA-256 해시를 검증합니다.

완료 후 `target\release\nsl.exe`와 `dist\nsl-win64.zip`을 사용할 수 있습니다. **`git push`만으로 빌드를 시작하지 않으며**, 소스 수정·커밋·푸시 작업과 바이너리 빌드·배포를 구분합니다. 특히 P2 모듈화 이후의 첫 빌드는 위 테스트와 독립 실행 환경의 GUI 검수를 마친 다음 진행하는 것이 안전합니다. 실행 중인 NSL의 EXE를 덮어쓰거나 사용자의 DB·설정·키·다운로드를 검증용으로 사용하지 마세요.

### 저장소 구성

```text
NSL/
├── src/                   Rust 앱·GUI·스캐너·파일 변환 소스
│   ├── app/               앱 기능별 모듈 구현 (10개 모듈 + mod.rs)
│   ├── container_index.rs  PFS0/HFS0 공통 읽기 전용 인덱스 파서
│   ├── main.rs            앱 상태, 공통 UI 함수, 진입점
│   └── runtime_tests.rs   앱 통합 회귀 테스트
├── assets/icon.ico        프로그램 아이콘
├── scripts/               ZIP 생성·검증 및 업데이트 스크립트
├── licenses/              포함된 외부 구성요소의 라이선스 고지
├── .github/workflows/     GitHub Actions 수동 Windows 빌드
├── build.rs               빌드 커밋 정보 삽입
├── build.bat              로컬 릴리스 빌드
├── Cargo.toml             Rust 프로젝트 설정
└── Cargo.lock             고정된 의존성 버전
```

빌드 결과물과 개인 설정·DB·키·게임 파일 등은 Git으로 배포하지 않습니다.

스토어는 `src/app/store.rs`, 다운로드는 `src/app/downloads.rs`, 전체 화면 흐름은 `src/app/frame.rs`에서 관리합니다. 앱 내부 10개 모듈의 상세한 역할과 의존성 원칙은 [앱 소스 구조](docs/architecture/NSL_APP_MODULES.md), 모듈화 시점의 검증 범위는 [P2 검수 기록](docs/qa/QA_MODULARIZATION_P2_2026-11-20.md)에 정리되어 있습니다.

롬 컨테이너 읽기 흐름, NSRP 참고 범위 및 엄격 검증/라이브러리 메타데이터 복구 정책은 [롬 컨테이너 파서 구조](docs/architecture/NSL_ROM_CONTAINER_INDEX.md)에 정리했습니다. 원본 NSRP 코드는 MIT 라이선스이며, 해당 저작권 고지는 `licenses/nsrp-MIT.txt`와 신규 배포 ZIP에 포함됩니다.

별도 빌드 없이 실행한 확장 검수의 범위와 한계는 [롬 파서 읽기 전용 검수 기록](docs/qa/QA_NSL_ROM_READONLY_VALIDATION_2026-11-20.md)에 정리했습니다. 실파일 검증을 강제하려면 `python -B scripts/qa-rom-index-readonly.py --require-corpus --mutations 2000`을 사용하세요.

## GitHub Actions 빌드 및 릴리스

GitHub Actions는 소스 푸시만으로 실행되지 않으며 **`workflow_dispatch` 수동 실행 전용**입니다. 저장소 코드를 커밋·푸시해도 실행파일·릴리스가 자동으로 갱신되지는 않습니다.

1. **[Actions → Build NSL for Windows](https://github.com/UzuCore/NSL/actions/workflows/windows-build.yml)**를 엽니다.
2. **Run workflow**를 누르고 `main` 브랜치를 선택합니다.
3. Windows 빌드·ZIP 무결성·자동업데이트 회귀 검사에 성공하면 아티팩트를 업로드하고, **그 수동 빌드 작업의 결과 ZIP을 GitHub Releases에 등록**합니다. 이 등록은 워크플로가 실행된 경우에만 수행됩니다.

릴리스 태그는 등록 시점의 한국 시간(KST)과 실행 번호로 만들어집니다.

```text
build-YYYYMMDD-HHMMSS-KST-r<실행번호>
```

프로그램의 **버전 표시는 숫자 버전이 아니라 Git 커밋 앞 7자리**입니다. 전체 40자리 커밋은 빌드 매니페스트에 기록됩니다. 따라서 화면의 커밋과 Releases 태그는 서로 다른 용도로 사용됩니다.

## 프로그램 업데이트와 데이터 보존

앱은 실행 시 백그라운드에서 최신 공식 GitHub Release를 확인합니다. 새 릴리스가 있을 때만 설치 안내를 표시하며, **다운로드·설치·재시작은 사용자가 승인한 경우에만 진행**합니다. `설정 → 일반 → 시작 시 새 버전 자동 확인`에서 자동 확인을 끄거나 다시 켤 수 있습니다. `도움말 → 업데이트 확인`으로 언제든 수동 확인할 수도 있습니다.

업데이트를 승인하면 공식 `nsl-win64.zip`을 내려받아 패키지의 **커밋 정보와 실행파일 SHA-256**을 검증합니다. 교체 직전에도 파일 무결성을 다시 확인하고, 실행 중인 NSL 프로세스가 종료된 후 같은 설치 폴더의 실행파일을 교체합니다. 일반 포터블 설치뿐 아니라 개발용 `dist\nsl.exe`와 `target\release\nsl.exe`도 해당 폴더 안의 실행파일만 교체합니다. 후자의 두 경로는 프로젝트 루트의 사용자 DB·설정을 계속 사용합니다.

자동 업데이트가 교체하는 파일은 다음 두 개뿐입니다.

```text
nsl.exe
nsl-manifest.json
```

**게임 파일, `library.db`, `config.json`, `prod.keys`, `title.keys`, 타이틀 DB, 아이콘·스크린샷 캐시, 다운로드 파일은 자동 업데이트 과정에서 덮어쓰지 않습니다.** 실행파일 교체 도중 실패하면 백업된 이전 파일로 복구하고, 가능한 경우 이전 버전을 다시 실행합니다. 실패 내역은 설치 데이터 폴더 아래 `temp\nsl_update_*\update-error.log`에 남습니다. 중요한 데이터는 별도로 백업하는 것을 권장합니다.

과거 ZIP 이름을 사용하는 구형 배포판은 Git 이력 및 배포 파일명 변경으로 자동 업데이트가 연결되지 않을 수 있습니다. 또한 **2026-11-19 수정 이전 버전**을 `target\release` 또는 `dist`에서 실행하는 경우에도 경로 검사 문제로 인앱 업데이트 적용이 실패할 수 있습니다. 이 경우 최신 ZIP을 한 번 직접 받아 **실행파일과 매니페스트만 기존 실행파일 폴더에 적용**하세요. 기존 사용자 데이터는 삭제하지 마세요.

## 라이선스 및 유의 사항

이 저장소의 `licenses/`에는 사용된 외부 구성요소의 라이선스 고지가 있습니다. 이는 **NSL 프로젝트 자체의 라이선스를 의미하지 않으며**, 프로젝트 코드에 대한 별도의 라이선스 파일은 현재 제공되지 않습니다.
